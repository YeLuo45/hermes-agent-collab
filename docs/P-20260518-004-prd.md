# P-20260518-004 PRD: deepcode-inspired Task Routing + SubTask Decomposition

## 1. Overview

**Project**: hermes-agent-collab

**Direction**: C  
**Inspiration**: deepcode — task complexity routing, parallel execution, dependency resolution, quality gates  
**Stage**: prd_pending_confirmation

## 2. Problem Statement

Current `decompose_task` uses LLM for all tasks regardless of complexity. Issues:
- Over-engineering for SIMPLE tasks (LLM decomposition is slow and expensive)
- No automatic routing based on `TaskComplexity` (SIMPLE/NORMAL/COMPLEX)
- SubTask dependencies resolved only by title-matching (fragile)
- No automated quality gates (CriticReview exists but unused in orchestration flow)
- No phase integration with existing OrchestrationPhase enum from Direction A

## 3. Proposed Solution

### 3.1 Task Complexity Router

Auto-route based on `TaskComplexity` (from Direction A):

| Complexity | Path | Behavior |
|------------|------|----------|
| SIMPLE | PENDING→EXECUTING→DONE | No decomposition; single SubTask or direct execution |
| NORMAL | PENDING→PLANNING→EXECUTING→DONE | Decompose into 2-4 SubTasks; parallel-friendly; no review gates |
| COMPLEX | PENDING→PLANNING→PLAN_REVIEW→EXECUTING→EXECUTION_REVIEW→DONE | Decompose into 4-8 SubTasks; CriticReview quality gates; retry on failure |

### 3.2 Rule-Based Decomposition for SIMPLE

SIMPLE tasks skip LLM decomposition entirely:
```python
def _route_simple_task(orch: TaskOrchestration) -> list[SubTask]:
    # Single SubTask matching the root task
    st = SubTask(
        sub_task_id=f"st_{uuid.uuid4().hex[:12]}",
        parent_orchestration_id=orch.orchestration_id,
        title=orch.user_task_description[:100],
        description=orch.user_task_description,
        assigned_agent_id=None,
        status=TaskStatus.PENDING,
        dependencies=[],
        result=None,
    )
    return [st]
```

### 3.3 Enhanced Decomposition for NORMAL/COMPLEX

LLM-based decomposition with structured output validation:
- Validate response schema before accepting
- Fallback to rule-based decomposition on parse failure
- For COMPLEX: inject `CriticReview` quality gates at PLAN_REVIEW and EXECUTION_REVIEW phases

### 3.4 Parallel Execution with Dependency Graph

SubTask execution order based on `dependencies` field:
- Build DAG (Directed Acyclic Graph) from dependency list
- Execute tasks in topological order
- Tasks with no dependencies run in parallel via `run_specialists_parallel`
- Retry failed tasks up to `retry_count` times

## 4. Design

### 4.1 New `TaskRouter` Class

```python
class TaskRouter:
    """Routes task execution based on complexity evaluation."""

    def route(self, orch: TaskOrchestration) -> list[SubTask]:
        """Returns SubTask list based on task complexity."""
        complexity_str = orch.context_pool.get("complexity", "normal")
        if isinstance(complexity_str, str):
            complexity = TaskComplexity(complexity_str)
        else:
            complexity = complexity_str

        if complexity == TaskComplexity.SIMPLE:
            return self._route_simple(orch)
        elif complexity == TaskComplexity.NORMAL:
            return self._route_normal(orch)
        else:
            return self._route_complex(orch)

    def _route_simple(self, orch) -> list[SubTask]: ...
    def _route_normal(self, orch) -> list[SubTask]: ...
    def _route_complex(self, orch) -> list[SubTask]: ...
```

### 4.2 Phase-Gated OrchestrationManager

Integrate phase transitions with SubTask lifecycle:

```
SIMPLE:  PENDING → EXECUTING → DONE
           ↓          ↓          ↓
        route()   exec_subtask  score

NORMAL:  PENDING → PLANNING → EXECUTING → DONE
           ↓          ↓           ↓         ↓
        route()   decompose()  exec_subtasks  score

COMPLEX: PENDING → PLANNING → PLAN_REVIEW → EXECUTING → EXECUTION_REVIEW → DONE
           ↓          ↓            ↓            ↓              ↓            ↓
        route()   decompose()   critic_gates  exec_subtasks  critic_gates  score
```

### 4.3 Orchestration Phase → TaskPhase Bridge

The existing `OrchestrationPhase` maps to `Phase` (from Direction A):
- `OrchestrationPhase.PLANNING` → routes to Phase.PLANNING
- `OrchestrationPhase.EXECUTING` → Phase.EXECUTING
- `OrchestrationPhase.REVIEWING` → Phase.PLAN_REVIEW / Phase.EXECUTION_REVIEW
- `OrchestrationPhase.COMPLETED` → Phase.DONE
