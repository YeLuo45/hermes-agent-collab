## 1. Overview / 背景

hermes-agent-collab 现有 Phase 1-4 已实现：工作区管理、Agent Profile、Task 生命周期、Skill 系统。当前 TaskManager 是单一 Agent 执行模式，不支持复杂任务的多 Agent 协同分解与审查。

本次迭代在现有架构基础上，新增 Coordinator → Specialist → Critic 三层编排，使系统能够处理需要任务分解、多角色并行执行、质量审查的复杂场景。

**非目标**：
- 不改变现有 REST API 接口（向下兼容）
- 不引入额外消息队列（继续用 subprocess + ThreadPoolExecutor）
- 第一期不实现权限体系

---

## 2. Goals / 目标

- **任务分解**：Coordinator 自动分析原始任务，输出子任务列表和依赖图
- **并行执行**：Specialist Agent 按依赖图并行执行子任务，互不阻塞
- **质量审查**：Critic 对每个 Specialist 结果评分，REJECT 触发重做
- **上下文共享**：所有 Agent 可访问同一个 Context Pool，实现信息共享
- **流式反馈**：WebSocket 实时推送分解计划、执行进度、审查结果

## 3. Core Features / 核心功能

### 3.1 新增数据模型

#### TaskOrchestration（编排记录）

```python
@dataclass
class TaskOrchestration:
    orchestration_id: str          # "orch_<uuid>"
    root_task_id: str              # 顶级任务 ID
    coordinator_id: str            # 负责分解的 Agent ID
    phase: OrchestrationPhase      # PLANNING | EXECUTING | REVIEWING | COMPLETED | FAILED
    sub_task_ids: list[str]       # 分解后的子任务 ID 列表
    context_pool: dict             # 共享上下文（所有 Agent 可读写）
    created_at: str
    updated_at: str
```

#### SubTask（子任务，元任务分解产物）

```python
@dataclass
class SubTask:
    sub_task_id: str
    parent_orchestration_id: str
    title: str
    description: str
    assigned_agent_id: str | None  # 认领的 Specialist
    status: TaskStatus             # pending | in_progress | completed | failed | rejected
    dependencies: list[str]        # 依赖的 sub_task_id 列表
    result: str | None             # 执行结果
    retry_count: int = 0           # 被 Critic 打回次数
    created_at: str
    updated_at: str
```

#### CriticReview（审查记录）

```python
@dataclass
class CriticReview:
    review_id: str
    orchestration_id: str
    sub_task_id: str
    critic_agent_id: str
    score: float                   # 0.0 - 10.0
    comments: str
    decision: ReviewDecision       # ACCEPT | REJECT
    created_at: str
```

#### ReviewDecision Enum

```python
class ReviewDecision(str, Enum):
    ACCEPT = "accept"
    REJECT = "reject"
```

#### OrchestrationPhase Enum

```python
class OrchestrationPhase(str, Enum):
    PLANNING = "planning"          # Coordinator 正在分解任务
    EXECUTING = "executing"        # Specialist 正在执行
    REVIEWING = "reviewing"        # Critic 正在审查
    COMPLETED = "completed"
    FAILED = "failed"
```

### 3.2 Coordinator — 任务分解

**触发时机**：用户创建任务时勾选"多Agent模式（Orchestration）"

**输入**：用户提供的任务 title + description

**输出**：
- `sub_tasks`：子任务列表（每个含 title、description、dependencies）
- `execution_plan`：执行顺序说明
- `context_pool`：初始共享上下文（从原始任务提取）

**实现**：
- 调用 subprocess AIAgent（provider: minimax-cn）
- Prompt 模板引导 Agent 输出结构化分解结果
- 解析 Agent 输出，还原为 SubTask 列表
- 展示分解计划，等待用户确认（5分钟倒计时）

**分解 Prompt 模板**（示意）：

```
你是一个任务分解专家。请将以下任务分解为 3-6 个可独立执行的子任务。

任务：{user_task_description}

请按以下 JSON 格式输出分解计划（不要添加任何解释）：
{{
  "sub_tasks": [
    {{"title": "...", "description": "...", "dependencies": []}}
  ],
  "execution_plan": "执行顺序说明",
  "context": {{"关键信息提取": "..."}}
}}
```

### 3.3 Specialist — 并行执行

**触发时机**：用户确认分解计划后

**执行规则**：
- Specialist 数量上限：3（可配置）
- 按依赖图拓扑排序选择可执行任务
- 无依赖或依赖全部完成的子任务立即分发
- 每个 Specialist 独立调用 subprocess AIAgent
- 完成后写入 `context_pool` 并更新 `sub_task.result`

**Agent 选择策略**：
- 根据 `sub_task.description` 匹配 `Agent.capabilities`
- 无匹配时使用默认 Agent（workspace settings）

### 3.4 Critic — 质量审查

**触发时机**：每个 Specialist 任务完成后自动触发

**评分规则**：
- 调用 subprocess AIAgent 评分
- Prompt 模板要求输出 0-10 分 + 理由
- 阈值：score < 6 → REJECT，≥ 6 → ACCEPT
- REJECT 时对应 SubTask status 设为 `rejected`，重试次数 +1
- 重试次数 ≥ 2 时不再打回，标记为 `failed`

**评分 Prompt 模板**（示意）：

```
你是一个代码审查专家。请对以下任务执行结果进行评分。

任务：{sub_task.title}
任务描述：{sub_task.description}
执行结果：{sub_task.result}

请按以下格式输出：
{{"score": 0-10, "comments": "评分理由", "decision": "accept/reject"}}
```

### 3.5 Context Pool — 共享上下文

**结构**：
```python
context_pool: dict = {
    "user_requirements": "...",     # 原始任务
    "key_decisions": [...],        # 关键决策记录
    "shared_artifacts": {...},     # 各 Agent 产出文件路径
    "execution_log": [...],        # 执行日志摘要
}
```

**访问控制**：
- 所有 Agent（Coordinator/Specialist/Critic）可读
- 仅 Specialist 执行时可写自己的产出章节
- Coordinator 汇总阶段可读不可写

### 3.6 WebSocket 流式反馈

**事件类型**：

| Event | Payload | 触发时机 |
|-------|---------|---------|
| `orchestration.created` | orch_id, root_task_id | 编排创建 |
| `orchestration.plan_ready` | sub_tasks[], execution_plan | Coordinator 分解完成 |
| `orchestration.user_confirmed` | orch_id | 用户确认分解计划 |
| `subtask.started` | sub_task_id, assigned_agent | Specialist 开始执行 |
| `subtask.completed` | sub_task_id, result | Specialist 完成 |
| `subtask.rejected` | sub_task_id, score, comments | Critic 打回 |
| `subtask.retry` | sub_task_id, retry_count | 重试触发 |
| `review.created` | review_id, sub_task_id, score, decision | 审查完成 |
| `orchestration.completed` | orch_id, final_report | 全部完成 |

### 3.7 结果汇总

**触发时机**：所有 SubTask 完成且无 `failed` 状态

**输出格式**（markdown）：

```markdown
# 任务执行报告：{root_task.title}

## 执行摘要
- 开始时间：{created_at}
- 完成时间：{completed_at}
- 总子任务数：{N}
- 通过数：{M}
- 重试数：{R}

## 子任务执行结果

### [SubTask 1] {title} ✅
- 执行者：{agent_name}
- 结果：{result}

### [SubTask 2] {title} ✅
...

## 共享上下文

{context_pool 内容}

## 审查摘要

| 子任务 | 评分 | 审查意见 |
|--------|------|---------|
| SubTask 1 | 8.5 | ... |
...
```

## 4. Technical Approach / 技术方案

### 4.1 技术栈（默认假设）

- **Backend**：Python FastAPI（现有项目）
- **Agent 调用**：subprocess AIAgent（现有方式，不引入新消息队列）
- **并发控制**：ThreadPoolExecutor（max_workers=3）
- **存储**：JSON 文件（现有 JsonFileStore 扩展）
- **前端**：现有 HTML/JS（WebSocket 改造）

### 4.2 新增文件

```
collaboration/
  models.py              # 新增 OrchestrationPhase, TaskOrchestration, SubTask, CriticReview
  orchestration_manager.py  # 新增 Coordinator/Specialist/Critic 编排逻辑
  events.py              # 新增编排相关事件类型
  collab_api.py          # 新增编排 REST 端点
  websocket_server.py    # 扩展 WebSocket 事件支持
```

### 4.3 新增 REST 端点

| Method | Endpoint | 说明 |
|--------|----------|------|
| POST | `/api/collab/orchestrations` | 创建编排任务（多Agent模式） |
| GET | `/api/collab/orchestrations/{orch_id}` | 获取编排详情 |
| GET | `/api/collab/orchestrations/{orch_id}/subtasks` | 获取子任务列表 |
| POST | `/api/collab/orchestrations/{orch_id}/confirm` | 用户确认分解计划 |
| POST | `/api/collab/orchestrations/{orch_id}/reject` | 用户拒绝分解计划 |
| GET | `/api/collab/orchestrations/{orch_id}/report` | 获取最终执行报告 |

### 4.4 核心流程时序

```
User → POST /orchestrations (multi_agent=true)
  → Coordinator AIAgent 分解任务
  → WebSocket: plan_ready
  → 5min 倒计时等待用户确认
  → User confirms (POST /confirm)
  → Phase: EXECUTING
  → ThreadPoolExecutor 分发 SubTasks（最多3并发）
    → Specialist AIAgent 执行
    → WebSocket: subtask.started / subtask.completed
    → Critic AIAgent 审查
    → WebSocket: review.created
    → if REJECT: subtask → retry (max 2)
  → 所有 SubTask 完成
  → Phase: COMPLETED
  → Coordinator AIAgent 汇总报告
  → WebSocket: orchestration.completed
```

## 6. Phases / 阶段划分

### Phase 1 — 编排基础架构
- 新增数据模型（OrchestrationPhase, TaskOrchestration, SubTask, CriticReview）
- 新增 `OrchestrationManager` 类
- 新增编排相关事件类型
- POST `/api/collab/orchestrations` 实现 Coordinator 分解逻辑
- WebSocket 推送 `orchestration.created` / `plan_ready`

### Phase 2 — 并行执行与审查
- ThreadPoolExecutor 分发 SubTask
- Specialist 执行逻辑（subprocess AIAgent）
- Critic 评分逻辑
- WebSocket 推送执行进度和审查结果

### Phase 3 — 结果汇总与展示
- Coordinator 汇总报告生成
- GET `/report` 端点
- 文档更新
